● That changes the shape a lot. The report isn't a list of articles — it's a set
  of topic briefings, each answering one standing question by synthesizing many
  articles into prose + citing them.

  Data model

  pub(crate) struct Report {
      generated_at: OffsetDateTime,
      model: String,
      window: String,              // "past 24h"
      briefings: Vec<Briefing>,
  }

  pub(crate) struct Briefing {
      question: String,            // "What's interesting in the Rust world this
  past day?"
      digest: String,              // Claude's synthesized markdown prose
      highlights: Vec<Highlight>,  // the few things that actually matter, each 
  linked
      sources: Vec<Source>,        // everything that fed the digest
      scanned: usize,              // how many entries were considered
  }

  struct Highlight {
      headline: String,
      detail: String,              // 1–2 sentences
      links: Vec<Url>,
  }

  struct Source { title: String, url: Url, feed: String }

  Report stays pure data with one method, to_markdown(&self) -> String. It's
  serde-serializable so JSON later is free — but no renderer trait / format enum
  now (one target, per your CLAUDE.md).

  What drives it: config topics

  Each topic = a question + which feeds to pull from (+ later, whether to also
  do generic web research):

  [[topic]]
  name = "rust"
  question = "What's going on interesting in the Rust world the past day?"
  feeds = ["Rust Blog", "This Week in Rust", "Lobsters"]

  [[topic]]
  name = "bicycle"
  question = "What's new and interesting in the bicycle world?"
  categories = ["cycling"]
  web_search = true   # later

  Pipeline (per topic)

  1. Rss → fetch entries in the time window from that topic's feeds/categories.
  2. (later) generic web research → more entries.
  3. Claude → given [{title, summary, link, feed}] + the question, return JSON {
     digest, highlights[] }.
  4. Push one Briefing into Report.
  5. report.to_markdown() → write to file (path from args/config) or stdout.

  This replaces request_something's free-text return with a structured JSON
  response you deserialize.

  Open points

  - v1 scope: RSS-only, leave web_search as a config field that does nothing
    yet? I'd say yes — ship the RSS path first.
  - Window: default past 24h, overridable with a CLI arg like --since 48h?
  - One Claude call per topic (simple, matches config, parallelizable) vs. one
    big call — I'd go per-topic.
